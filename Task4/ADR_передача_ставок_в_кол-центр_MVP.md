### <a name="_qmphm5d6rvi3"></a>**Решение**

- Диаграмма контекста (C4 L1): [c4_context.puml](c4_context.puml) — копия контекста Task3; добавлена передача актуальных депозитных ставок внешнему (партнёрскому) кол-центру (подсвечено тегом «Изменения Task4»).
- Диаграмма контейнеров (C4 L2): [c4_containers.puml](c4_containers.puml)

**Контекст (C4 L1).** Состав участников — как в решении Task3: все системы банка показаны единой системой «Информационная система банка», внешними остаются СМС-шлюз телеком-оператора, Система оператора связи и Партнёрский кол-центр. Отличие Task4: добавлена передача актуальных депозитных ставок партнёрскому (внешнему) кол-центру файловым обменом; внутренний оператор консультирует клиентов по актуальным ставкам депозитов. Новый обмен ставками детализируется на уровне контейнеров.

**Контейнеры (C4 L2).** Диаграмма — копия диаграммы контейнеров Task3; добавленный контейнер передачи ставок подсвечен цветом (тег «Изменения Task4») и вынесен в легенду. Из Task3 в диаграмму включён контейнер `Сервис мониторинга`, который в Task4 дополнительно покрывает границу обмена с партнёрским кол-центром.

**Логика решений и выбор технологий.**

1. **Единый источник истины — Сервис депозитов (NFR-3).** Ставки уже перенесены в Сервис депозитов и ведутся через Рабочее место ведения ставок (Task3). Передача в кол-центры строится поверх этого, без ручного Excel и без участия АБС (NFR-3).
2. **Внутренний кол-центр — через Kafka (как в Task3).** Система кол-центра уже интегрирована с Kafka (потребляет заявки с сайта), поэтому ставки передаются тем же транспортом: Сервис депозитов публикует событие об изменении ставки, а новый микросервис приёма событий системы кол-центра пишет локальную модель ставок (NFR-1, NFR-5). Оператор получает быстрый интерфейс (NFR-1) и работает даже при кратковременной недоступности источника (NFR-2).
3. **Партнёрский кол-центр — файловый обмен по SFTP (NFR-4).** Партнёр — внешняя система другого подрядчика, API-вызовы невозможны, поэтому компонент банка «Экспорт ставок» формирует файл со ставками и выкладывает его на SFTP-сервер обмена; партнёр забирает файл по расписанию (pull-модель). Такой вариант минимизирует входящие доступы во внутреннюю сеть банка и упрощает контроль периметра.
4. **Переиспользование технологий (NFR-5).** Компонент «Экспорт ставок» — на стеке Сервиса депозитов (.NET) — не требует новых технологий; микросервис кол-центра — Java Spring Boot + PostgreSQL, что совпадает с платформой системы кол-центра и имеющейся Java-экспертизой в команде АБС.
5. **Надёжность и идемпотентность (NFR-2).** События в Kafka версионируются, повторная публикация не создаёт дублей; файл содержит версию и контрольную сумму, а обработка повторно загруженного файла устойчива.
6. **Наблюдаемость (NFR-5).** Публикация событий, формирование и выгрузка файлов, а также факт забора партнёром журналируются и покрываются метриками; задержка доставки вызывает алерт. Сбор метрик и алертинг возлагаются на `Сервис мониторинга` (Task3), который дополнительно покрывает границу обмена с партнёром.
7. **Безопасность (NFR-4).** Партнёру передаются только ставки (без ПДн); доступ к SFTP — по ключам с ограничением по IP; канал шифруется. Ведение ставок доступно только депозитному бэк-офису.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| № | Альтернатива | Почему отклонена |
| :-: | :- | :- |
| A-1 | Прямой доступ системы кол-центра к БД Сервиса депозитов (SQL) | Нарушает разграничение доступа и ИБ (NFR-4), создаёт жёсткую связность и обходит прикладной API; невозможно переиспользовать механику событий. |
| A-2 | REST-вызовы системы кол-центра к Сервису депозитов вместо Kafka | Синхронная связность и меньшая устойчивость; система кол-центра уже использует Kafka (заявки с сайта), поэтому событийный путь переиспользует существующую интеграцию (Task3). |
| A-3 | API/REST-интеграция с партнёрским кол-центром | Невозможна: партнёр — внешняя система другого подрядчика, API-вызовы не поддерживаются; обмен возможен только файлами. |
| A-4 | Передача ставок партнёру вручную (e-mail/Excel), как в текущем процессе | Ставки будут неактуальными, высок риск ошибок, не масштабируется при росте звонков; противоречит цели цифровизации. |
| A-5 | Предоставить партнёру доступ к интерфейсу/системе банка | Нарушает требования ИБ и периметр банка; внешний подрядчик не должен иметь доступ во внутренние системы. |
| A-6 | Общая папка (SMB) или обычный FTP вместо SFTP | Небезопасно (нет шифрования/нормальной аутентификации) и плохо поддерживается в периметре; выбран SFTP (SSH). |
| A-7 | Публиковать ставки в кол-центры из АБС | Противоречит Task3: АБС перегружена и не является источником истины по ставкам; ставки вынесены в Сервис депозитов. |
| A-8 | Push-модель (банк сам отправляет файл на SFTP партнёра) | Требует исходящих доступов к инфраструктуре внешнего подрядчика и усложняет контроль/аудит; pull-модель через SFTP банка безопаснее и проще. |

**Недостатки, ограничения, риски**

- **Задержка доставки партнёру.** Файловый обмен не в реальном времени: между выгрузками ставки у партнёра могут отставать от банка. Требуется согласованный регламент частоты обмена (NFR-1) и, при необходимости, выгрузка при каждом изменении.
- **Расхождения между источниками отображения.** Оператор кол-центра видит локальную модель, а не источник напрямую; при пропущенном событии возможны расхождения. Компенсируется отметкой времени обновления в интерфейсе (NFR-2).
- **Периметр и управление ключами.** SFTP-сервер и внешний партнёр требуют настройки сетевых доступов, ротации ключей, ограничения по IP и аудита; ошибки конфигурации — риск для ИБ (NFR-4).
- **Зависимость от внешнего партнёра.** Соблюдение формата и частоты обмена зависит от партнёрской стороны; нужны тестовый обмен (UC-5) и контроль квитирования (UC-4).
- **Устаревание данных без мониторинга.** Без алертов на задержку события/выгрузки проблема обнаруживается только по жалобам клиентов; необходима наблюдаемость (NFR-5).
- **Стоимость сопровождения.** Появляется новый микросервис приёма событий системы кол-центра и компонент «Экспорт ставок» — требуются мониторинг, деплой, резервное копирование и сопровождение силами банка и подрядчика системы кол-центра.
- **Ограничение области MVP.** Заявки и «особые» персональные ставки по-прежнему обрабатывает бэк-офис (Task3); в MVP кол-центр консультирует по текущим базовым ставкам, полная автоматизация — на целевом горизонте.
