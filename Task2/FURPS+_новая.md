| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F-1 | Сайт: список депозитов с актуальными ставками; подача заявки (телефон, Ф. И. О.), заявка передаётся в кол-центр для предложения особых условий | Требуется интеграция «сайт → система кол-центра»; публичный канал без аутентификации |
| F-2 | Интернет-банк: список депозитов с актуальными и персонализированными ставками; подача заявки (счёт, сумма) с подтверждением СМС-кодом | Задействует СМС-функционал ядра; персонализация требует правил расчёта ставок |
| F-3 | СМС-уведомления клиенту после подтверждения ставки и после открытия депозита | Гарантированная доставка критична для подтверждения |
| F-4 | Ведение, согласование и подтверждение ставок в едином сервисе вместо XLS (доступ бэк-офиса депозитов); в MVP заявку обрабатывает и условия подтверждает менеджер бэк-офиса | Единый источник истины (Сервис депозитов), замена Excel/ручного согласования |
| F-5 | Идентификация нового клиента в отделении до открытия депозита | |
| F-6 | Сквозная передача заявок и ставок между сайтом, интернет-банком, системой кол-центра и АБС | Ключевая интеграционная функция |
| U   | Удобство использования (Usability) |              |
| U-1 | Максимально удобный и быстрый интерфейс; единые UX-паттерны для сайта и интернет-банка | Один продукт — два канала, отклик UI критичен |
| U-2 | Соответствие корпоративной дизайн-системе (привычные цвета, брендированные элементы) | Требование бизнеса |
| R   | Надёжность (Reliability)           |              |
| R-1 | Доступность сервисов 24/7 на уровне 99,9 %; при сбое ЦОД — переключение на резервный ЦОД | Требование бизнеса; возможность уже есть: два ЦОД |
| R-2 | Нагрузка онлайн-заявок не должна влиять на работоспособность АБС и её БД | АБС перегружена; прямая интеграция ставит под угрозу доступность банка |
| R-3 | Гарантированная доставка СМС-кодов и уведомлений | Влияет на подтверждение операций |
| R-4 | Сохранность заявок при сбоях и защита от дублей (durability, идемпотентность) | Повторные отправки и ретраи могут создать дубли депозитов |
| R-5 | Мониторинг доступности и алертинг | **Доп.** Соблюдение 99,9 % невозможно подтвердить без наблюдаемости |
| P   | Производительность (Performance)   |              |
| P-1 | Отклик интерфейса на действия пользователя — не более 200 мс; для операций с обращением к внешним системам (подача заявки, получение ставок) — не более 1–2 с | Бизнес требует «миллисекунды»; 200 мс — порог восприятия «мгновенно», 1–2 с допустимо для сетевых операций |
| P-2 | Устранить загрузку справочных данных дольше 1 секунды при проведении платежей | Кэширование справочников |
| P-3 | Горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД | |
| P-4 | Выдерживать целевую (пиковую) нагрузку и рост числа клиентов | |
| P-5 | Изоляция нагрузки онлайн-заявок от БД АБС | АБС масштабируется только вертикально |
| S   | Поддерживаемость (Supportability)  |              |
| S-1 | Преимущественно использовать существующие технологии банка (MS SQL, Oracle, .NET, Java, React, PHP); новые — только совместимые с текущими платформами и с имеющейся в банке экспертизой | Использование знакомых стеков снижает стоимость и риски сопровождения |
| S-2 | Заложить возможность перехода на очереди сообщений (Kafka) и микросервисную архитектуру интернет-банка в рамках задачи открытия депозитов | Kafka «на перспективу»; текущая платформа интернет-банка с ней несовместима (+R-3) |
| S-3 | Возможность доработки силами команды банка (ядро интернет-банка, система кол-центра) | Снижение зависимости от подрядчиков |
| S-4 | Инженерные практики: документация для расширения системы, версионирование, CI/CD и управление конфигурацией | **Доп.** Документация нужна для расширения разными командами (банк и подрядчики); без CI/CD релизы MVP не масштабируются |
| +R  | + Ограничения (Restrictions)       |              |
| +R-1 | Запрет прямой работы интернет-банка с API/БД АБС в новом процессе | |
| +R-2 | Ограничения платформ: интернет-банк — монолит на одной группе серверов (+резервный ЦОД) и несовместим с Kafka; АБС масштабируется только вертикально | Влияет на выбор транспорта интеграции и схемы масштабирования |
| +R-3 | Зависимость от подрядчиков: обновление ядра интернет-банка и доработка СМС-функционала привязаны к подрядчику — доработок желательно избежать | |
| +R-4 | Безопасность и регуляторика: разграничение доступа к данным депозитного и кредитного бэк-офиса, личная идентификация нового клиента, шифрование чувствительного трафика на сайте и в интернет-банке | |
| +R-5 | Сроки: MVP ~6 месяцев, целевое состояние ~1 год | |
